# Limitations — Glance Fashion Image Retrieval

Honest assessment of where the current pipeline design falls short of its objectives, and what would fix each gap.

---

## Limitation 1: No per-garment color binding (critical)

### What's wrong

The pipeline extracts a **single dominant color** per image using KMeans on the center crop. For images with multiple garments (e.g., a red tie AND a white shirt), the metadata only stores `color: ["red", "white"]` — it doesn't know *which* garment has *which* color.

### Why it matters

Query 5 — *"A red tie and a white shirt in a formal setting"* — is the headline compositional test. Two images:

| Image | Colors | Garments | attr_match score |
|---|---|---|---|
| Red tie + white shirt (correct) | red, white | tie, shirt | 2.0 + 1.5 = 3.5 |
| Red shirt + white tie (wrong) | red, white | shirt, tie | 2.0 + 1.5 = 3.5 |

Both score identically. **The reranker cannot distinguish them.** The system fails on the exact test it was designed to pass.

### Why it exists

Zero-shot CLIP + KMeans gives per-image attributes, not per-object attributes. We don't have object detection in the pipeline.

### What would fix it

Add an object detection step before color extraction:
1. Run **Grounding DINO** or a pretrained fashion object detector on each image
2. Segment individual garments (tie, shirt, jacket, etc.)
3. Run KMeans color extraction on each segmented region independently
4. Store per-garment color bindings: `[{"type": "tie", "color": "red"}, {"type": "shirt", "color": "white"}]`
5. The reranker then checks per-garment color match instead of bag-of-colors

This is the single highest-impact improvement available.

## Limitation 2: Pseudo-label noise degrades reranker signal

### What's wrong

Location and style labels are generated by zero-shot CLIP against fixed prompts — no ground truth, no validation. CLIP can misclassify:

- A street photo with a brick wall → tagged "office" (wall resembles indoor textures)
- A casual outfit in a stiff pose → tagged "formal"
- An indoor studio with natural lighting → tagged "park" (green backdrop + sunlight)

### Why it matters

Query 2 — *"Professional business attire inside a modern office"* — needs `location=office AND style=formal` to filter correctly. If 30% of "office" tags are wrong, the reranker demotes correct candidates and promotes wrong ones. The location and style weights become **noise amplifiers**, not signal.

### Why it exists

No dataset provides location or style labels. Zero-shot CLIP is the pragmatic choice but has no accuracy guarantees. Fashion images are often shot in studios with plain backgrounds — CLIP has little scene context to work with.

### What mitigates it

- **Confidence threshold**: Only apply location/style rerank when `loc_conf > 0.5` or `style_conf > 0.5`. Below that, set the weight to 0.
- **Manual spot-check**: Inspect 50 images and report actual pseudo-label accuracy. If accuracy is below 60%, the location/style rerank should be deprioritized in evaluation.
- **Upgrade path**: Replace zero-shot CLIP with a fine-tuned scene classifier (Places365 or a small model trained on 200–300 manually labeled images).

## Limitation 3: KMeans color picks the wrong dominant color

### What's wrong

KMeans on the center crop assumes the garment is centered. When it isn't:

- **Full-body image, small accessory near center**: KMeans picks the accessory color (scarf, bag), not the main garment
- **Dark background, light clothing**: Background pixels outnumber clothing pixels → KMeans picks background color
- **Multiple garments of different colors**: The largest cluster may be neither — it could be the color of the background or an intermediate between two garment colors

### Why it matters

Query 1 — *"Bright yellow raincoat"* — if the raincoat is at the bottom of the frame, the center crop might cover the model's face and background. KMeans tags the image `color=gray` (background). The reranker gives `color_match=0` even though the raincoat is clearly yellow. The image scores lower than it should.

### Why it exists

Color extraction without object detection has no notion of "which region is the garment." Center cropping is a heuristic that works for standard fashion photography but fails on non-centered compositions.

### What mitigates it

- **Fallback to CLIP color prompts**: If KMeans confidence is low (<30% pixel fraction for the dominant cluster), run CLIP zero-shot against color names and use that instead.
- **Color extraction on full image**: Instead of center crop, run KMeans on the full image and take the top-2 clusters that aren't near-gray (to exclude background).
- **Upgrade path**: This problem also goes away with object detection + per-segment color extraction (same fix as Limitation 1).

## Limitation 4: Query parser can't handle style-only queries

### What's wrong

*"Casual weekend outfit for a city walk"* (Query 4) has no explicit garment, color, or location keywords. A keyword-based parser returns:

```python
{"color": [], "garment": [], "location": null, "style": "casual"}
```

The attribute match score is approximately 0 for this query. The pipeline degrades to vanilla CLIP.

### Why it matters

The system claims to be better than vanilla CLIP, but for query 4 it **is** vanilla CLIP. The evaluation must report this honestly — claiming improvement here would be misleading.

### Why it exists

Keyword-based extraction can only find attributes that have explicit surface forms. Style-only queries are inherently hard because "casual" and "city walk" are abstract concepts, not concrete tokens.

### What mitigates it

- **LLM-based parser (upgrade path)**: A small LLM can infer implicit attributes — it knows "city walk" implies urban outdoor, "weekend" implies casual.
- **Honest reporting**: Report that Query 4 is CLIP-dependent and the reranker contributes nothing. This is not a failure — it's a demonstration that you understand your system's boundaries.

## Limitation 5: Hand-tuned reranker weights overfit to the 5 queries

### What's wrong

The reranker weights (`color=2.0, garment=1.5, location=1.0, style=0.5`) were chosen by intuition, not learned from data. They were tuned against the 5 evaluation queries.

### Why it matters

These weights may be optimal for the 5 evaluation queries but suboptimal for a broader set of queries. The system appears to perform better than it actually would on unseen queries. This is a form of **test set overfitting**.

### Why it exists

No labeled training data exists for learning weights. The 5 evaluation queries are both the optimization target and the measurement — a known methodological flaw.

### What mitigates it

- **Report multiple weight configurations** in the ablation study:

| Weights | Query 1 | Query 2 | Query 3 | Query 4 | Query 5 |
|---|---|---|---|---|---|
| Uniform (all=1.0) | P@5 | P@5 | P@5 | P@5 | P@5 |
| Color-heavy (color=3.0) | P@5 | P@5 | P@5 | P@5 | P@5 |
| Garment-heavy (garment=3.0) | P@5 | P@5 | P@5 | P@5 | P@5 |
| Chosen (c=2,g=1.5,l=1,s=0.5) | P@5 | P@5 | P@5 | P@5 | P@5 |

Show that the chosen weights are reasonable but not magical.

- **Acknowledge in the report**: "Weights were manually chosen. A learned reranker (cross-encoder) with relevance judgments would be the production approach."

## Limitation 6: No learned reranker

### What's wrong

The reranker uses a hand-weighted scoring function. It cannot capture interactions between attributes (e.g., "red shirt AND blue pants" is different from "red shirt AND red pants" — the latter should get a style penalty but our simple scorer doesn't know that).

### Why it matters

Hand-weighted rules are transparent but brittle. They can't learn from data, can't adapt to query patterns, and don't generalize to unseen attribute combinations.

### Why it exists

Training a learned reranker requires labeled relevance judgments (query → ranked results with relevance scores). We don't have any.

### What mitigates it

- Acknowledge this is the obvious next step.
- Propose using the 5 evaluation queries + manual relevance judgments as a seed set for training a small cross-encoder.

## Summary

| Limitation | Severity | Impact on objectives | Fix difficulty |
|---|---|---|---|
| No per-garment color binding | **Critical** | Pipeline fails query 5 — the headline compositional test | Medium — add Grounding DINO |
| Pseudo-label noise | **High** | Reranker adds noise for queries 2 and 4 | Low — confidence threshold + manual spot-check |
| KMeans picks wrong color | **Medium** | Lowers recall on color-specific queries | Low — fallback to CLIP color prompts |
| Query parser blind to style-only | **Medium** | Pipeline = vanilla CLIP for query 4 | Low — honest reporting |
| Hand-tuned weights overfit | **Medium** | Reported performance may not generalize to unseen queries | Low — report multiple weight configs |
| No learned reranker | **Low** | Not blocking — hand weights work for the task | High — needs labeled relevance data |

**The honest take**: The pipeline is a strong attempt that makes genuine improvements over vanilla CLIP for most queries. Its critical gap is per-garment color binding — without it, query 5 remains partially unsolved. Every other limitation is manageable through confidence thresholds, fallbacks, and honest reporting. The project should be evaluated on its architectural reasoning and clean evaluation methodology, not on perfect query 5 performance.
